# Контроллер 1 (Phoenix Contact, OPC UA) не подключается: не работают ни запись, ни чтение

Дата наблюдения: 2026-08-24, стенд поднят через `start-all.ps1 -Mode docker` в `scada-editor-backend`.

## Контракт: что должно быть верно, чтобы запись/чтение тегов работали у оператора

Это не про конкретную реализацию — реализуйте как удобно, важны наблюдаемые гарантии:

1. **Успешное подключение к контроллеру не должно зависеть от того, что симулятор успел
   стартовать раньше шлюза.** Если шлюз стартовал первым или контроллер временно недоступен —
   он обязан САМ добиться подключения после того, как контроллер станет доступен, без
   перезапуска шлюза руками. (Сейчас механизм для этого есть — супервизор каждые 10 c — но в
   этом инциденте он не привёл к подключению за много минут при доступном порту 4840.)

2. **Один недоступный/зависший контроллер не должен блокировать переподключение остальных.**
   Если у шлюза несколько контроллеров (сейчас 2 — OPC UA и Modbus), проблема с одним не
   должна ронять или замораживать обслуживание другого — это подтверждено рабочим (Modbus
   ходит), но подключение к OPC UA зависает бессрочно без таймаута — то есть гарантия сейчас
   держится случайно, не заложена явно.

3. **Команда записи (`writeTag`) должна либо применяться, либо возвращать причину отказа за
   разумное фиксированное время** (сейчас — да, `FAILED_NO_CONNECTION` приходит быстро; это
   работает и его ломать не нужно) — но при этом:

4. **Если контроллер не подключён дольше N секунд, это должно быть видно без доступа к
   консоли живого Java-процесса** — то есть в `event_log` (БД) или другом постоянном месте,
   которое можно посмотреть после инцидента. Сейчас факт «висим уже 10+ минут» виден только
   косвенно (по отсутствию новых `CONNECTED`), а не прямым сообщением — из БД нельзя
   отличить «ещё не успел» от «завис навсегда».

5. **Запись через `writeTag` в RW-тег должна приводить к свежей телеметрии по этому же
   тегу** (DataChange от симулятора → republish в Kafka `scada.tags`) — сквозной цикл
   `команда → ПЛК → onChange` в `runtime` зависит именно от этого; частичная работа
   (запись прошла, но обновление не пришло, или наоборот) недопустима.

Ниже — конкретные наблюдения и код, которые объясняют, где сейчас это не выполняется.

## Симптом

Команда записи тега `Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST` (и любого другого OPC UA-тега
на контроллере 1) стабильно возвращается в топик `scada-command-results` со статусом:

```json
{"status":"FAILED_NO_CONNECTION","success":false,"message":"Контроллер не подключён"}
```

При этом:
- Modbus-контроллер (id=2, WAGO) работает нормально — его теги (`RT_PAR_F[...]` и другие,
  1877 шт.) идут в Kafka (`scada.tags`) непрерывно, со свежими метками времени.
- OPC UA-контроллер (id=1, Phoenix Contact) не даёт **ни одного** сообщения телеметрии
  ни по одному из своих 594 тегов — то есть проблема не только в записи, чтение тоже мертво.

## Что НЕ является причиной (проверено и исключено)

- ~~Конфиг симулятора~~ — `plc-simulator/config/replay_config.yaml` содержит корректный
  `access: RW` без `generator: replay` для тегов 385/389 (LINE1V0.ST, LINE1V10.ST), правка
  из демо 07.08.2026 жива и используется (Dockerfile жёстко запускает
  `python simulator.py config/replay_config.yaml`).
- ~~Рассинхрон анонсируемого endpoint~~ — исключено, см. пункт 4 выше.
- ~~Гонка при старте контейнера~~ — исключено, см. пункт 3 (симулятор был готов заранее).
- ~~Проблема на стороне Kafka/consumer~~ — исключено: Modbus-контроллер на том же брокере,
  в том же топике, работает без сбоев.

## Гипотеза (не подтверждена независимо, нужна проверка разработчиком)

`connectOpcUaController` (строка 303) делает два блокирующих вызова без таймаута:

```java
List<EndpointDescription> endpoints = DiscoveryClient.getEndpoints(controller.getEndpoint()).get();
...
OpcUaClient client = OpcUaClient.create(config);
client.connect().get();
```

Оба `.get()` — на `CompletableFuture` без `.get(timeout, unit)`. Если сервер отвечает на TCP,
но чем-то не устраивает клиента Milo на уровне OPC UA handshake (не наш случай на первый
взгляд — симулятор явно готов, — но версии протокола / порядок SecureChannel могут не совпасть
после пересборки образа симулятора), такой вызов **виснет навсегда**, а не падает по таймауту.

Дальше это важно из-за двух мест, где вызывается `connectOpcUaController`:

- **При старте** (`@PostConstruct init()`, строки 172-189) — синхронно, в цикле по всем
  контроллерам. Если бы связь c контроллером 1 зависла тут навсегда, контроллер 2 (Modbus)
  вообще не подключился бы (тот же цикл, следующая итерация). Но Modbus работает — значит
  **на старте зависания не было**, попытка вернулась (успешно или с ошибкой) быстро.
- **При переподключении супервизором** (`superviseConnections`, `@Scheduled` каждые 10 c,
  строка 198) — здесь `connectOpcUaController(controller, false)` вызывается на **общем пуле
  планировщика Spring**. Если у планировщика 1 поток (дефолт Spring Boot, если явно не
  сконфигурирован `TaskScheduler`/`spring.task.scheduling.pool.size`), а любой из `.get()`
  когда-нибудь зависнет на одной из повторных попыток — **все** `@Scheduled`-задачи гейтвея
  (включая супервизор для *других* контроллеров и `logHealthSummary`) встанут намертво вместе
  с ним. Это архитектурный риск независимо от того, является ли он причиной именно этого
  случая.

**Проверить разработчику:**
1. Сколько потоков в пуле планировщика (`spring.task.scheduling.pool.size`, дефолт Spring
   Boot = 1). Если 1 — это уже само по себе стоит поднять, ниже почему.
2. Поднять уровень логов до DEBUG для `org.eclipse.milo` на следующем зависании и посмотреть,
   на каком именно шаге handshake зависает `client.connect()` — это единственный способ
   подтвердить или опровергнуть гипотезу без доступа к консоли живого процесса.
3. Добавить `jstack` живого процесса шлюза в момент воспроизведения — если поток супервизора
   стоит в `Object.wait`/`park` внутри `DiscoveryClient.getEndpoints` или `client.connect`, это
   прямое подтверждение зависшего `.get()`.

## Рекомендуемые изменения (независимо от точной причины — оправданы сами по себе)

1. **Таймаут на оба блокирующих `.get()`** в `connectOpcUaController`:
   ```java
   DiscoveryClient.getEndpoints(controller.getEndpoint()).get(5, TimeUnit.SECONDS);
   ...
   client.connect().get(5, TimeUnit.SECONDS);
   ```
   Без этого один зависший контроллер может остановить переподключение всех остальных.

2. **Выделенный `TaskScheduler` с пулом ≥ 2-3 потоков** для `@Scheduled`-задач гейтвея —
   единственный поток по умолчанию не должен разделяться между супервизором нескольких
   контроллеров и служебными задачами (`logHealthSummary`).

3. **Видимость неудачных тихих переподключений.** Сейчас `connectOpcUaController(..., false)`
   логирует отказ только через `log.debug(...)` (строка 350) — не в `event_log`, не в Kafka
   `EventProducer`. При диагностике «почему не подключается» это означает полное отсутствие
   следов в БД, только консоль живого процесса (у которого, в отличие от `runtime`, тоже нет
   файлового логирования). Стоит хотя бы бросать одно `WARNING`-событие в `event_log` раз в
   N неудачных попыток (по аналогии с троттлингом в `markControllerDown`, строка 167-169), а
   не молчать полностью.

4. **Несогласованность между полом опроса и записью** (отдельная, не связанная с этим
   инцидентом находка, `OpcUaClientServiceDB.java:378-383`):
   ```java
   private void startOpcuaPolling(ControllerEntity controller, ExecutorService executor, long gen) {
       final Long cid = controller.getId();
       executor.submit(() -> {
           OpcUaClient client = opcClients.get(cid);   // захвачен ОДИН раз при старте задачи
           while (isCurrentPoll(cid, gen)) {
               ...
               client.read(...)                         // всегда тот же объект
   ```
   а `writeOpcUa` (строка 754) каждый раз делает **свежий** `opcClients.get(controllerId)`.
   Пока `opcClients` меняется только вместе с перезапуском поллинга (`reconnectOpcUa` глушит
   старый поток и стартует новый) это безопасно, но это неявный инвариант — если когда-нибудь
   появится путь, меняющий `opcClients` без пересоздания поллинг-потока, чтение и запись
   начнут расходиться по тому, какой клиент считается «текущим». Стоит либо всегда брать
   клиента из карты в `startOpcuaPolling`, либо задокументировать инвариант явно.
