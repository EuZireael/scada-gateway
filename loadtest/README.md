# Нагрузочное тестирование SCADA-шлюза

Config-driven harness: выбираешь профиль → он генерит согласованную пару конфигов,
поднимает стек, снимает метрики в CSV, гасит стек.

## Что тестируется

```
симулятор (OPC UA + Modbus)  →  ШЛЮЗ  →  Kafka (scada-telemetry)
```

Монитора в этом стеке **нет** — меряем сторону производства (шлюз + Kafka):
*реально ли шлюз выдаёт ожидаемый поток телеметрии, или «не успевает».*
Consumer-lag монитора — отдельный тест, с поднятым монитором.

Ключевой факт: телеметрия шлюза — **firehose**, каждый тег шлётся каждый цикл
(не on-change). Поэтому поток предсказуем:

```
ожидаемый поток ≈ число_тегов / (poll_ms / 1000)   сообщений/с
```

Две ручки нагрузки: **число тегов** и **частота опроса** (poll_ms).

## Быстрый старт

```bash
cd loadtest
python3 run.py smoke          # дымовой: 1000 тегов, ~1000 msg/s, 2 мин
python3 run.py stress_opcua   # лестница OPC до колена
python3 run.py stress_modbus  # лестница Modbus (последовательное чтение — узкое место)
python3 run.py wave           # спайк: симулятор то пропадает, то возвращается
python3 run.py soak           # 4 часа ровной нагрузки + chaos (утечки)
```

Флаги: `--keep` (не гасить стек после теста), `--build` (пересобрать образы).

Результат: `loadtest/metrics/<профиль>_<время>.csv` + сводка по ступеням в консоли.

## Профили

Правятся в [`profiles.yaml`](profiles.yaml). Поля: `protocol` (opcua|modbus|mix),
`tags` или `ladder` (лестница размеров), `poll_ms`, `duration_s`/`step_duration_s`,
`mix_opc` (доля OPC при mix), `wave`, `chaos`. Свой тест — просто добавь профиль.

## Как читать CSV

| колонка | смысл | на что смотреть |
|---|---|---|
| `produced_rate` | реальный поток в Kafka, msg/s | ← главное |
| `achieved_pct` | % от ожидаемого (tags/poll) | **падает ниже ~90% → колено** (шлюз не успевает) |
| `heap_mb` | heap шлюза | на soak: **не возвращается к базе после GC → утечка** |
| `cpu_pct`, `threads` | CPU и число потоков | рост потоков без спада — тоже утечка |
| `gc_count`, `gc_time_s` | сборки мусора | резкий рост частоты GC = давление на память |
| `note` | событие (пауза/chaos) | привязка провалов к событиям |

Где ждать стены (по коду шлюза):
- **Modbus** — самый жёсткий предел: 1877+ тегов читаются ПОСЛЕДОВАТЕЛЬНО, по одному
  round-trip, в один поток. Цикл перестаёт укладываться в интервал → achieved_pct падает.
- **OPC UA** — выше: один батч `read()` на все теги контроллера.
- **Kafka** (одна нода) — десятки–сотни тыс. msg/s для мелких сообщений.

## Генератор отдельно

```bash
python3 gen_config.py --tags 20000 --poll-ms 200 --protocol mix --mix-opc 0.7
```
Пишет пару в `generated/`: `controllers.yaml` (шлюз) + `sim.yaml` (симулятор) с
гарантией совпадения id (OPC `ns=2;s=<id>` ↔ `address`; Modbus `40001+2j` ↔ регистр `2j`).

## Как это устроено / подводные камни (Fedora + podman)

- **Подмена конфигов без пересборки:** `docker-compose.loadtest.yml` монтирует
  сгенерированные конфиги внутрь контейнеров. Шлюз: `SPRING_CONFIG_IMPORT=file:/config/controllers.yaml`
  переопределяет встроенный `classpath:controllers.yaml` (грузятся ТОЛЬКО нагрузочные теги).
- **DOCKER_HOST:** `run.py` сам подставляет podman-сокет (`/run/user/<uid>/podman/podman.sock`).
- **SELinux Enforcing:** bind-mount конфигов помечен `:Z` — иначе контейнер их не прочитает
  и шлюз молча возьмёт встроенные 2471 тега.
- **Флаги через env:** шлюз читает флаги через `@Value("${gateway.persist-telemetry}")`.
  Это НЕ relaxed binding — env-имя `GATEWAY_PERSIST_TELEMETRY` (`.`/`-` → `_`).
  Нагрузочный override принудительно: `persist-telemetry=false` (изолируем Kafka от
  Postgres) и `alarms.enabled=false` (алармы жгут CPU/поток опроса).
- **Свежесть образа:** `run.py --build` (или `./up.sh`) пересобирает образ из текущего
  кода. Старый образ может не иметь актуальных флагов/оптимизаций → тест соврёт.

## Прогрев базы

`smoke` уже проверен на живом стеке: 1000 тегов @1000ms → **~960 msg/s (96% плана)**,
подмена конфига и сбор метрик работают.
