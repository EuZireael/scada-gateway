# Контракт: телеметрия по исключению (шлюз → Kafka → монитор)

> 02.10.2026. Ветка `feat/telemetry-by-exception`. Реализовано в Java-шлюзе
> (`TelemetryPublishFilter`); **версия на Rust обязана соблюдать этот же контракт** — на него
> опирается монитор (`scada-editor-backend`, сервис `runtime`).

## Зачем

Раньше шлюз публиковал в Kafka **каждый тег на каждом цикле опроса**, изменился он или нет.
Нагрузочный стенд (10 копий проекта «Танки нормализации молока», 27 400 тегов, опрос 2 с) давал
≈13 700 сообщений/с, почти все — повтор прежнего значения. Монитор тратил основную работу на
разбор и раздачу повторов: при ~100 операторах значения на экране опаздывали на 5–17 с.

После перехода на отправку по исключению: ≈1 100 сообщений/с на том же стенде (из них ≈910 —
полная отправка раз в 30 с), задержка значения на экране p50 56 мс / p95 346 мс, CPU монитора
втрое меньше.

## Правила публикации значения тега

Значение тега **публикуется в Kafka**, если выполнено хотя бы одно (проверяются по порядку):

1. **Первое значение тега** после старта шлюза.
2. **Сменилось качество** (GOOD ↔ BAD и т. п.) — обрыв и восстановление связи публикуются сразу.
3. **Прошло `full-resend-ms`** с последней публикации этого тега — **полная отправка**:
   неизменившееся значение повторяется, чтобы потребитель знал, что тег жив, и чтобы после
   своего перезапуска получил значения всех тегов не дольше чем за этот период.
4. Если с последней публикации прошло меньше `min-interval-ms` — **не** публиковать (антидребезг;
   0 — выключено). Изменение, отрезанное этим окном, не теряется: оно уйдёт первым же опросом
   после окна, если значение не вернулось.
5. **Значение изменилось** относительно последнего **опубликованного** (не предыдущего опроса!):
   - числа: `|новое − опубликованное| > зона`, где
     `зона = max(deadband, |опубликованное| · deadband-percent / 100)`;
     при нулевой зоне — **любое** отличие;
   - не числа (строки, bool): на равенство.

Сравнение с последним **опубликованным** значением, а не с прошлым опросом, — чтобы медленный
дрейф внутри зоны не терялся, а накапливался до порога.

Интервалы (п. 3, 4) считаются **по часам шлюза** (момент получения значения), а не по метке
источника: OPC UA не двигает метку, пока значение стоит, и полная отправка по ней не наступила бы.
В само сообщение метка источника уходит как раньше.

Состояние «последнее опубликованное значение / качество / время» — **на тег, в памяти шлюза**.
После перезапуска шлюза оно пустое, поэтому каждый тег сначала публикуется (п. 1).

**Недостоверное значение** (value = null, quality = BAD) проходит через те же правила, только
если включена отправка BAD-кадров (`gateway.send-bad-frames=true`). Если она выключена, BAD-кадр
не публикуется и **не** запоминается как опубликованный.

Формат сообщения, ключ (имя тега) и топик **не меняются**. Сжатие в Kafka — snappy.

## Настройки (`application.yaml`, секция `gateway.publish`)

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `enabled` | `true` | `false` — прежнее поведение: каждый тег каждый цикл |
| `deadband` | `0` | абсолютная зона нечувствительности |
| `deadband-percent` | `0` | относительная, % от опубликованного значения |
| `min-interval-ms` | `0` | не чаще раза в N мс на тег; 0 — без ограничения |
| `full-resend-ms` | `30000` | полная отправка неизменившихся; разумно 30 000–60 000 |

Поканальные переопределения `history:` из `controllers.yaml` относятся **только** к локальной
истории шлюза и на публикацию в Kafka **не** влияют.

## Обязательства потребителя (монитор `runtime`) — для понимания связки

- `runtime.telemetry.max-silence-ms` (по умолчанию 40 000) **должен быть больше**
  `full-resend-ms`. Это время, которое неизменившийся тег может молчать, не считаясь мёртвым.
- Фоновые задачи считают вход устаревшим только после `max(stale_after_ms, max-silence-ms)`
  тишины. Потерю связи с ПЛК шлюз сообщает **качеством BAD сразу** (п. 2) — по тишине
  обнаруживается только смерть самого шлюза.
- При подключении к топику монитор читает сообщения за последние `max-silence-ms` и берёт
  последнее значение на тег — поэтому полная отправка (п. 3) обязательна: без неё после
  перезапуска монитора неизменившиеся теги были бы «нет данных».
- В WebSocket к операторам монитор шлёт только изменения и раз в 5 с тишины — «пульс».

**Если менять `full-resend-ms` — менять и `max-silence-ms` монитора**, иначе фоновые задачи
начнут ложно уходить в «устаревший вход».

## Что ещё нашёл нагрузочный стенд в Java-шлюзе (учесть в версии на Rust)

Стенд: 20 контроллеров по 2740 тегов (54 800 тегов), источник — `plc-simulator`, треть тегов
меняется каждую секунду (≈18 000 изменений/с).

1. **Загрузка `controllers.yaml` через окружение Spring съедает память.** Файл подключается
   `spring.config.import`, и Spring раскладывает каждое поле каждого тега в отдельное имя
   настройки (`opcua.servers[3].tags[1234].name`) и держит их всё время работы: 2,5 млн объектов
   `ConfigurationPropertyName`, ≈45 объектов на тег. На 54 800 тегах куча 1,5 ГБ заполнена
   полностью, сборщик мусора занимает ≈11 ядер, опрос идёт впятеро реже положенного.
   **Конфигурацию тегов читать отдельным парсером, а не через механизм настроек фреймворка.**
2. **Запись локальной истории — на треде опроса.** При ≈18 000 изменений/с и зоне истории 0
   история пытается писать ≈18 000 строк/с, пул соединений БД (10) исчерпан, запись ждёт по 30 с —
   и **вместе с ней стоит опрос контроллеров**. Медленная БД истории не должна останавливать сбор
   данных: писать историю асинхронно, через ограниченную очередь (с прореживанием или сбросом при
   переполнении и метрикой отставания), отдельным пулом.
3. **Один замок на соединение `host:port` в PAC-клиенте.** Контроллеры с одинаковым адресом
   опрашиваются строго по очереди. В жизни у каждого ПЛК свой адрес, но если несколько логических
   контроллеров смотрят в один PAC — соединение должно быть на контроллер.
4. **Lua-снимок PAC компилируется заново на каждом опросе** (`Globals.load` → `LuaC.compile`
   ответа на 2740 строк). Разбирать ответ без компиляции — заметная экономия CPU и мусора.
